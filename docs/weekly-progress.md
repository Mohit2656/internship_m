# Weekly internship progress

Weekly reports supplement the existing monthly photo reports. Monthly endpoints,
files, reviews and historical attendance are preserved.

The internship start and end dates are both included. Weeks are
`ceil((daysBetween(start, end) + 1) / 7)`. The end must be strictly after the start.
For 1 November–30 December 2026 there are 60 days and 9 weeks; week 9 runs
27–30 December. UTC calendar arithmetic gives the same result in the browser.
The server ignores the legacy `totalWeeks` request value and calculates it from
the dates. `durationMonths` remains the existing separate registration field.

New and edited registrations allow at most 520 weeks (10 years), bounding the
number of records generated by a single request. Older internship details remain
readable through their existing APIs even if they exceed this new generation
limit; weekly generation requires dates within the limit. Mentor and IIIC views
show a per-student date-review warning for unsupported legacy ranges while
continuing to show other students' weeks. No historical dates
are changed by the migration.

Periods are generated in the registration transaction at
`INTERNSHIP_DETAILS_COMPLETE`, the same stage that enables monthly reports.
Existing completed registrations are backfilled when the weekly view is opened.
An internship row lock and a unique internship/week/date key prevent duplicate
periods across retries and concurrent requests. Matching active periods perform
no writes. The final week ends at the actual internship end date.
Backfilling also normalizes the saved derived `total_weeks` value for valid
registrations, keeping existing report exports consistent without changing
internship dates or student update timestamps.

Date edits retain matching periods and archive superseded empty periods. Once a
period has any submission, including a rejected report, its dates cannot change.
An edit affecting such a period returns `409 SUBMITTED_WEEK_DATE_CONFLICT` and the
whole registration transaction rolls back. An extension can add or adjust empty
tail periods while retaining submitted weeks and their identifiers. No period,
report or revision is deleted by date reconciliation.

Students submit text reports for started, active weeks. New reports await the
currently assigned faculty mentor. Only rejected reports may be resubmitted;
the client must send the current revision. Mentor decisions also require that
revision and an active assignment, and rejection requires a reason. IIIC/Admin
can monitor all periods and decisions. Every submission and decision stores its
actor, timestamp, revision and work description in immutable history.

Attendance counts are read-only summaries of existing records. Automatic
absences do not count as submissions. GPS counts use the separate
`attendance_evidence.location_verification_status = VERIFIED` signal; an overall
verified or liveness-verified record alone does not imply GPS verification.
Weekly report review does not approve attendance or change workplace approval.

API endpoints (under `/api/v1`):

- `GET /student/weekly-progress`: registration overview, active/archived periods,
  report state, attendance summary and revision history.
- `POST /student/weekly-progress/{periodId}`: JSON `workDescription`, plus
  `revision` when correcting a rejected report.
- `GET /mentor/weekly-progress`: `{weeks, warnings}` for currently assigned students.
- `POST /mentor/weekly-progress/{periodId}/approve`: JSON `revision`.
- `POST /mentor/weekly-progress/{periodId}/reject`: JSON `revision`, `reason`.
- `GET /admin/weekly-progress`: institution-wide `{weeks, warnings}` monitoring.

`WEEKLY_REPORT_SUBMITTED` is routed to the active assigned mentor through the
existing durable mentor inbox. `WEEKLY_REPORT_APPROVED` and
`WEEKLY_REPORT_REJECTED` are routed to the student inbox. Event keys contain the
period and revision, so retries cannot duplicate notifications. Report, audit and
notification rows share one transaction; failed transactions publish no alerts.
Existing notification polling, unread counts and mark-read APIs are reused.

Migration: `V37__weekly_internship_progress.sql`. No new environment variables,
dependencies, paid services or deployment topology changes are required.
